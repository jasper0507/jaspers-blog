## 真冲突

读者在技术文章页上可能吃亏的分歧。这是本轮要逐项验证的主体。

### C1 — 中文正文字形：系统宋体 vs「网页不要用宋/楷」

**原文：** 宋体和楷体不适合网页，细节会被锯齿取代；不会选就用苹方/雅黑；若为美观更推荐[思源黑体 CJK](https://source.typekit.com/source-han-sans/)（标点间距）。另外点名思源宋体横画过浅，白底上横几乎消失。

**本站：** `.post-body` 走 `--font-serif`：自托管 Source Serif 4（**仅拉丁**）→ `Songti SC` / `STSong` → `Source Han Serif SC` / `Noto Serif CJK SC`。ADR-0013（2026-08-27）明确不自托管中文、禁止字体 CDN。标题与 `strong` 为 600/700；宋体系通常没有这些字重，浏览器会**伪粗**。`font-synthesis: weight` 只写在代码元素上，拦不住正文/标题。

**为何是真冲突：** 技术长文的汉字落在系统宋上。这正是原文说会在网页上丢细节的那类字形；栈里还预备了原文点名「横画浅」的思源宋。中英混排时拉丁是 Source Serif 4、汉字是另一套宋，笔画粗细和字面大小不一致。Q2 已冻**衬线角色**，但把中文继续交给 Songti SC 是开放的工程题。

**验证：** 视觉。公开资源只能看「别人的宋/黑」，看不到「本站纸色 + 你的系统回退」。

| 公开样张                                                              | 看什么                                           |
| --------------------------------------------------------------------- | ------------------------------------------------ |
| 原文折叠样张（同页 SN Pro / Times / **SimSun** / KaiTi）              | 网页宋体长文是否「锯齿、磕绊」                   |
| [Noto Serif SC](https://fonts.google.com/noto/specimen/Noto+Serif+SC) | 思源宋横画是否过浅（原文警告）                   |
| [Noto Sans SC](https://fonts.google.com/noto/specimen/Noto+Sans+SC)   | 思源黑长文是否更像空气、标点是否更稳             |
| [Haku 原文页](https://re.karlbaey.top/articles/typography/)           | 作者实际采用的「衬线标题 + 无衬线正文」          |
| 本站 `artifacts/visual/post/post-1440-light.png`                      | 当前衬线正文在验收机上的样子（不等于你的系统宋） |

**原型：** 决策前用 `/prototype/cjk-body/` 四档对照，选定后已删除，不进生产。

**状态：** 采纳并落地。拉丁 Source Serif 4 + 自托管 Noto Sans SC 分包（`npm run fonts:fetch`）。系统黑体仅作回退。

### C2 — 未开 `text-autospace`

**原文：** 汉字与英文之间应有空隙；可用 [`text-autospace`](https://developer.mozilla.org/zh-CN/docs/Web/CSS/Reference/Properties/text-autospace)，或手敲空格。手敲属写作层，本轮只审 CSS。

**本站：** `.post-body` 未设该属性。浏览器默认目前仍是不自动加缝（需 opt-in）。Haku 正文写了 `text-autospace: ideograph-alpha ideograph-numeric`。

**为何是真冲突：** 技术文章持续中英数混排。没有缝时「函数foo」会粘成一块，增加扫读阻力。这是范围内、可落在 `.post-body` 的 CSS。

**验证：** 文字即可讲清机制与风险；公开演示确认观感。

| 公开样张                                                                                                     | 看什么                        |
| ------------------------------------------------------------------------------------------------------------ | ----------------------------- |
| [MDN `text-autospace`](https://developer.mozilla.org/zh-CN/docs/Web/CSS/Reference/Properties/text-autospace) | 属性本身的交互演示            |
| [Haku 原文页](https://re.karlbaey.top/articles/typography/)                                                  | 已开启时的中英缝              |
| [赫蹏](https://sivan.github.io/heti/)                                                                        | JS 版中西混排（对照，不引入） |

**要点（文字）：**

- 2026 年主流新版可开 `normal` / 开关级取值；细粒度关键字（`ideograph-alpha` 等）各引擎参差。稳妥写法是 `.post-body { text-autospace: normal; }`，代码和公式排除。
- `replace`（把已有 ASCII 空格收成细缝）基本未实现。作者若已手敲空格，开启后可能**略宽一截**。
- 代码、行内码、KaTeX 必须关掉，否则 `for循环` 类标识和公式会被插缝。

**原型：** 不需要。

**状态：** 采纳（已写入 `.post-body { text-autospace: normal; }`，代码/行内码/KaTeX 为 `no-autospace`）

### C3 — 行高 1.62 对中文衬线是否偏紧

**原文：** 别吝惜行间距；作者自己也在 `1.625` 与 `1.7` 之间反复。失败案例是行距被脚注顶乱、块与块贴死。

**本站：** `.post-body` 为 `1.125rem`（18px）/ `line-height: 1.62`。脚注已用 `line-height: 0`，不是原文那张「行距乱动」图。Haku 是根字号 17px、`line-height: 1.75`。

**换算：** 本站行盒约 18×1.62=29.2px，Haku 约 17×1.75=29.8px，**绝对行盒几乎一样**；本站字更大，所以比例更紧。若中文继续走宋体（笔画密），1.62 可能偏挤；若改无衬线，1.62 往往够用。因此本条挂在 C1 后面。

**验证：** 文字先定「要不要动」；若动，用 Haku 原文页当公开对照。改数值才需要并排原型。

**状态：** 拒绝（维持 1.62）

### C4 — 列表项距为 0，块与块是否偏紧

**原文：** 折叠块、blockquote、段落之间要有可感知的空隙；贴在一起会窒息。本站没有原文那种 admonition，但列表是正文常客。

**本站：** `li + li { margin-top: 0 }`；`p`/`ul`/`blockquote`/`table` 为 `0.78em 0`；`blockquote` 另有 `margin-block: 1.7em`；`details`/`pre` 为 `1.35em`。列表内部比段间明显更紧。

**验证：** 看本站验收图即可，不必另找公开页：`artifacts/visual/post/post-1440-light.png` 第一节的无序/有序列表。若那张图里列表读起来不挤，本条可拒绝。

**原型：** 仅当验收图看不准时，做 `li` 间距 0 / 0.35em / 0.5em。

**状态：** 拒绝（维持列表项距 0）

### C5 — 代码块圆角卡片是否把正文挤成配角

**原文：** 失败排版里「图片和代码块喧宾夺主，正文像临时工」。后面又说代码常常是正文的一部分，**不要**折叠或移出文档流——原文这里自相拉扯。本站代码留在流内，符合后一句；冲突只在「视觉权重」。

**本站：** `.astro-code` 有边框、`0.65rem` 圆角、可选标题条、行高亮/diff 色带。Kraft 身份的一部分，不是 GitHub 默认灰块。

**验证：** 视觉。公开对照：

| 公开样张                                                                    | 看什么                                       |
| --------------------------------------------------------------------------- | -------------------------------------------- |
| [Haku 原文页](https://re.karlbaey.top/articles/typography/) 里的 CSS 代码块 | 更扁、更少圆角时是否更「让路」               |
| 本站 `artifacts/visual/post/post-1440-light.png`                            | 三块代码（普通 / 高亮 / diff）相对段落的重量 |
| [Tailwind Typography](https://tailwindcss-typography.vercel.app/)           | 大众方案的代码重量（不当成目标）             |

**原型：** 仅当公开对照不够。变体应是「现状 / 去圆角去标题条 / 更小字号」，不是把代码移出文档流。

**状态：** 拒绝（维持 Kraft 代码卡片）

## 弱冲突

原文有字，但不是可执行规范，或本站已基本满足。仍纳入讨论；默认建议拒绝，由作者逐项拍板。

### W1 — 「长文用系统无衬线」vs 衬线正文角色

原文给不会选字的人的默认：苹方 / Inter / Noto Sans。本站故意用衬线正文（ADR-0020 / 0014），Q2 已冻这个角色。中文图书本身就是宋+黑，并不是「衬线不能长读」。公开对照：Haku（无衬线正文）vs 本站验收图 vs [Retypeset](https://retypeset.radishzz.cc/)（排版向主题）。公开对照仍可用；本站四档原型里的 `system-sans` 是同一篇文章的全文系统黑，可与衬线三档直接比。

**状态：** 拒绝（选了衬线拉丁 + 中文黑体，不是全文系统黑）

### W2 — 目录在左 vs 在右

原文：「如果你正在我的网站上阅读，页面中应该只有左侧的目录」——描述 Haku，不是「目录必须在左」。本站目录在阅读栏**右侧**外侧，`position: fixed`，≥1280px（实现为 `min-width: 80rem`）才显示，不占阅读栏。功能符合「配角滚出文档流」。公开对照：Haku 原文页（左）vs 本站验收图（右）。**建议拒绝。**

**状态：** 拒绝（维持右侧目录）

### W3 — 「字太小」

原文失败案例是字过小。本站正文 18px，比 Haku 的 17px 更大。**建议从真冲突中排除。** 若觉得仍小，并入 C3 一起看，不要单独加字号。

**状态：** 拒绝（18px 已大于 Haku，不单独加字号）

### W4 — 链接珊瑚且默认无下划线

原文：不要在标题/链接上乱贴大红大绿；一个主色就够。本站链接用的就是那条珊瑚，符合「一个主色」。缺的是默认下划线（hover 才有）。Haku 链接带下划线。这是可发现性，不是原文硬性条目。**建议拒绝**；若要做，只加 underline，不改颜色。

**状态：** 拒绝（维持 hover 才下划线）

### W5 — 「绿色是大忌」vs 代码字符串/diff 绿

`--code-string` 为绿系，`diff.add` 也是绿。原文禁的是品牌/标题/链接上的绿，不是语法色。Haku 自己的 tip 就是绿。改掉字符串绿会削弱扫代码的效率，还可能和珊瑚链接撞色。**建议拒绝。**

**状态：** 拒绝（维持绿字符串 / 绿 diff.add）

### W6 — 次要图片「破版」出文档流

原文：非必要的长图应离开文档流，可参考 mediawiki 式 `mwfigure`（行为不稳定）。本站 `img` 只做 `max-width: 100%` + 段距，无 `figure`/`figcaption`、无浮动。仓库里目前没有文章插图；ADR-0016 允许外链图，所以这是**潜伏项**。无图就没有读者伤害。**建议暂缓**，等真实插图出现再开。

**状态：** 暂缓（无真实插图前不开）
